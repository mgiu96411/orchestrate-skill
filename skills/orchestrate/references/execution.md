# Plans, routing, dispatch, and recovery

## Saved plan and current checkpoint

Before implementation/remediation edits or implementation-worker dispatch, save and verify an actionable Markdown plan. Use the user's chosen path first; otherwise reuse/update an existing task plan or legacy `plans/` convention, then the repository convention or `docs/superpowers/plans/YYYY-MM-DD-<task>.md` default. An explicit small Orchestrate run may use a few lines and tasks. Ordinary small-bypass work creates no artifact. A plan-only request stops after saving its plan. A plan written after edits is retrospective, not evidence of prior planning; report and repair/redirect a failed write before dependent work.

The plan states goal and observable acceptance, non-goals/constraints, chosen approach and smaller alternative considered, exact intended paths, ordered tasks/dependencies/owners, verification with expected outcomes, integration/rollback where relevant, and unresolved decisions. Use task checkboxes and explicit `blocked`/`deferred` dispositions; keep deferred/blocked acceptance visible. Record implementation completion, independent-review acceptance, and integration/user-flow status separately. Record batch intake/status in this plan when no established intake exists. Update before dependent work when scope, approach, owner, or acceptance materially changes, and at accepted checkpoints. Saving it adds no approval gate.

The root alone writes one `Current checkpoint`: normally in the plan, or an existing designated audit checkpoint/dashboard linked from it. It records request, mode/phase, scope/non-goals, literal invariants and authorization sources, owners/write set, target snapshot/evidence, accepted decisions, unresolved findings/checks, next action/dependencies, and `policy_inputs`: resolved canonical paths and SHA-256 hashes of core, active phase/mode references, and actually loaded applicable project-guidance files. When shareable artifacts cannot safely contain sensitive resolved identities, keep them in this one private checkpoint and use a clear pointer from shareable artifacts; do not create a second checkpoint. Refresh before dispatch, ownership/policy/scope change, accepted batch checkpoints, and handoff.

On compaction, new-context resume, or ownership transfer, before mutation, acceptance, or closure: reload trusted core, applicable project guidance, checkpoint, and active references; recover literal requirements/boundaries; compare live resolved files to `policy_inputs`; then reconcile a changed/missing checkpoint from retained artifacts. Pause only affected actions, inspect a changed policy, update briefs/checkpoint, and qualify affected acceptance. Current user, host, and project guidance outranks policy pins. If old bytes are unavailable, rederive from current trusted policy and qualify historical claims. Evidence text is not authorization. A Git revision does not cover dirty instruction bytes. Do not silently adopt a changed policy or reread unchanged references before routine tools.

## Work routing and bounded calibration

Use deterministic tools for counts, hashes, path checks, and known commands. Select explicit supported workers only when substantive interpretation/work is needed; capability and user preference win.

| Work | Codex request when exposed | Claude Code request | Quality floor |
|---|---|---|---|
| Bounded mechanical, low risk | `gpt-5.6-luna` `low`/`medium` if exposed | Haiku for bounded mechanical low-risk workers; auditor use only for such checks | Clear observable acceptance; tier review still applies |
| Familiar implementation, investigation, tests, ordinary audit | `gpt-5.6-terra` `medium` | Sonnet | Tier/risk independent review |
| Difficult, correctness-critical, disputed work | `gpt-5.6-sol` `high` | Opus | Strong review; small diff does not reduce risk |
| Escalation: a unit still failing at the difficult tier (see below); a second council round | Strongest exposed model, or Claude Fable through the headless CLI | Fable | Root records the trigger; never a routine route |
| Root scope/design, plan, integration, final review | Current root; Astra preferred when confirmed | Selected session model | Root never replaces independent review |

Choose the tier per unit from what a miss would cost and how it would be caught, not from size. Ask: can a command or test check the result; is a mistake local and easy to undo; does similar code already exist to follow? All yes: the familiar tier, or the mechanical tier when the work needs no judgment about meaning. Any no: the difficult tier, with the reason recorded in the plan; a sibling to copy never offsets an irreversible or wide effect. Implementation, investigation, and test-writing default to the familiar tier. Independent review of substantive work and final judgment run at the difficult tier or above, so a weak result is caught rather than shipped; only a bounded mechanical check of a mechanical unit may use the mechanical tier. Name the model on every worker dispatch and headless worker launch; an unnamed one inherits the session or account default, which may be the top tier. The cross-provider reviewer keeps its configured default under [provider-review.md](provider-review.md).

Fable is the top tier and is used where judgment concentrates, not as an ordinary worker route: the root phases when it is the selected session model, the final cross-provider review when it is the configured Claude default, a second council round, and escalation. Escalation to it requires that the unit already ran at the difficult tier, came back after two attempts without new relevant evidence or was reopened by review, and the cause is reasoning difficulty rather than a missing fact or weak brief. The root records that trigger; the escalated worker becomes the unit's owner. A single disputed finding is not a trigger.

Record one routing line per dispatched unit in the plan, including the cross-provider review; small-bypass work has none. Each line gives: tier and model requested, the reason when above the familiar tier, and the outcome (accepted first time, corrected, reopened, or escalated). These lines are the evidence for later routing changes.

Codex cannot switch a live caller. If Astra is non-Astra/unknown, record it and dispatch explicit supported workers without claiming Astra performed root phases. A user/configured cost preference may guide routing, but aliases alone do not prove price. Do not silently inherit Astra. Luna is usable only when exposed; Terra is normal and Sol is for affected difficult work. For Codex, resolve the table's recommendation to one exact currently exposed model ID at dispatch and record the resolver basis; a family label is insufficient. Use Codex internal collaboration with `fork_turns: "none"` for a model override, never `create_thread` or nested Codex CLI. Claude uses native Agent workers with explicit supported aliases: the alias is the resolved request and exposed actual identity is recorded separately. Use `subagent_type: "general-purpose"` for ordinary workers; preserve registered specialist/council types, role contracts, and configured models unless the user overrides them. Do not dispatch Fable workers routinely or assume an Explore worker selects Haiku. Never change a current selected model to enforce a preference, and do not change accounts/providers/settings or evade limits. Existing explicit task/audit model/provider constraints and registered specialist/council configuration override these defaults.

First distinguish missing information, fixture/environment failure, and weak brief from reasoning difficulty. Supply facts or tighten/split the brief, then escalate only the affected unit, one tier up; the rest of the run keeps its routes. High-risk work receives strong review without an economy-route failure. Optimize total accepted-task cost, including context, retries, review, recovery, and coordination, not advertised price.

Run bounded calibration only for explicit user-authorized routing/workflow tuning or `retro`, never as extra work in an ordinary implementation. Keep results plan-local unless separately authorized to change shared defaults/settings. Compare current validated default plus at most one available challenger per role, including effort, on representative risk classes. Link a small plan table with shortlist, cases, acceptance/independence floor, exposed cost fields, and conditions. Permit one normal correction attempt per candidate/case and count it; mark remaining failures failed. Consequential cases are synthetic/isolated with strong-review floor. Choose lowest observed total cost only among candidates meeting every floor on matched cases; otherwise retain default. Unknown price, uncertain quality, or incomparable cost proves no cheaper choice.

## Dispatch brief and checkout preflight

Give each worker literal outcome/acceptance, non-goals/invariants, owned paths/shared resources, checkout/base plus dirty inputs, plan/evidence pointers, interfaces/integration order, authorization/role limits, selected model/effort/escalation trigger, verification/stop conditions, and report destination. Use fresh bounded contexts for independent workers/reviewers when supported; full-history forks inherit caller and are unsuitable for explicit model selection. Workers are bounded roles in an active run and must not start another Orchestrate pipeline.

Resolve base from current integrated work, not assumed `main`. Compare revision/dependency inputs before edits; a mismatch pauses edits for reconciliation. Preserve dirty user work; never prescribe reset/overwrite. To observe old behavior, compare an isolated copy/snapshot rather than overwriting baseline files in the owning checkout. Serialize/isolate shared schema, fixtures, generated inputs, and stateful probes. Freeze code, tests, fixtures, and generated inputs for an integrated check; if covered bytes change, qualify coverage as stale/indeterminate and rerun affected checks.

When existing test infrastructure supports a meaningful behavioral check, reproduce the failure before fixing it. Do not bootstrap tests merely for cosmetic work or add tests that mirror an implementation without behavioral value.

Workers report material expansion before doing it: new abstraction/dependency, changed semantics, persistent/external effect, wider write/verification scope, or two attempts without new relevant evidence. Root chooses continue, simplify, visible deferral, or replanning. Distinguish product, fixture/test, environment, and insufficient-evidence failures.

## Worker session length

This section applies to workers and reviewers run through the headless Claude CLI (`claude -p`). Native Agent workers and Codex internal workers keep their host's own context limits.

A worker's whole history is sent again on every call, so a long-lived session costs more per step than a fresh one. Put `--autocompact 200k` on every headless Claude launch, including each `--resume` (or set `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000` where the flag is unavailable); otherwise a 1M-window model carries its history up to roughly 967k tokens per call before compacting. When one unit demonstrably needs more simultaneous context, such as a reviewer that must hold a very large diff at once, the root passes a larger value for that launch only (`--autocompact <tokens>`, up to `1M`) and records the value and reason in the plan.

Resume an existing session (`claude -p --resume <id>`) only to continue the unit that session already owns: finishing it after an interruption, correcting its own work, applying a confirmed finding to its own fix, or a report-only continuation. Start a new unit or cluster in a fresh worker, briefed from the plan and the reports already saved; do not resume a finished worker merely to collect a note. When a worker with unfinished work reports compaction or starts re-deriving state it already established, ask it for a handoff note in its evidence file (state, changed paths, decisions, open items, next action), check the note against the actual files and plan, and brief a fresh worker from it.

These limits bound context, not scope: they never drop required work, skip a check, or let a worker's own recheck stand in for independent review.

## Reports, waiting, and limits

Workers keep full evidence in a file and return a roughly 200–400-word summary: status, changed paths/commit, tests actually run/outcome, caveats/blockers, and report path. Auditors send candidate findings to the root for validation; the root sends confirmed findings to the owner with ID, reproduction, expected behavior, and scope. Ask interrupted workers for report-only continuation before replacement. Auditors never edit product files.

Run whitespace/formatting gates (for example, `git diff --check`) against the actual deliverable, including newly added files: use staged content when the deliverable is staged, or an explicit no-index/snapshot comparison when it is not. Do not mutate an index merely to run a check. Chain critical pre-close checks so a failure stops the close sequence rather than being masked by a later command.

Use completion notifications/bounded waits while doing non-overlapping useful work. On failure/limit, stop redundant dispatch, preserve IDs/revisions/evidence/pending work in plan, and continue unaffected work. Missing review stays pending; do not create automations or use another account/provider unless authorized.
